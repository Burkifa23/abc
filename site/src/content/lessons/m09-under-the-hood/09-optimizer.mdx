"Turn the optimizer on" sounds like one switch, but it is really three stages that run in order on your contract:

1. **Codegen-level** choices made while the compiler first turns Solidity into code.
2. **Yul-level** transformations of the intermediate representation.
3. **Opcode-level** clean-up of the final instruction stream.

Knowing which stage does what makes the settings in your build configuration understandable, rather than folklore.

## Why bother, and what changes

The optimizer simplifies complicated expressions, which shrinks code and cuts execution cost. Smaller code means cheaper deployment, and cheaper execution means cheaper calls later. It also specialises and inlines functions. Inlining can make code bigger, but it is done anyway because it exposes more simplifications.

The most visible difference between an optimized and an unoptimized build is that constant expressions are computed at compile time: `60 * 60 * 24` simply becomes one number. In the assembly output (compare `--asm` with `--asm --optimize`) you will also see duplicate blocks merged. In the Yul output (compare `--ir` with `--optimize --ir-optimized`) the difference can be dramatic: functions get inlined, combined or rewritten to drop redundancy.

The flag `--optimize` switches on the opcode-based optimizer for the generated bytecode and the Yul optimizer for Yul the compiler produces internally (for instance for the ABI coder). A couple of steps, like the peephole optimizer and the unchecked loop increment, are on by default and can only be disabled through Standard JSON. And an empty step sequence (just a colon) is accepted even without `--optimize` to turn off the user-supplied part of the Yul sequence, because the unused-pruner runs regardless.

## The `runs` parameter

`--optimize-runs` (or `optimizer.runs` in JSON) is the most misunderstood setting. It is *not* the number of optimization rounds. The optimizer repeats as long as it can still improve things. Instead, `runs` is your estimate of **how often each opcode of the deployed code will execute over the contract's lifetime**.

That makes it a trade-off between deployment cost and execution cost:

- A small value, such as 1, tells the compiler "this code barely runs": pick **short** code even if each execution is expensive. Good for something deployed once and called a handful of times.
- A large value says "this code runs constantly": pick **longer but cheaper-to-run** code. Good for a hot contract called millions of times.

The maximum is 2^32 - 1. A frequent mistake is setting it to the maximum "to optimize as much as possible"; that just means you pay extra bytes at deployment (and risk the code-size limit) for cheapness you may never cash in.

```json
{ "optimizer": { "enabled": true, "runs": 200 } }
```

## The opcode-based module

This oldest module works on assembly. It cuts the instruction list into **basic blocks** at every `JUMP` and `JUMPDEST`, because inside a block control flow is straight. For each block it records every change to the stack, memory and storage as an *expression*: an instruction plus pointers to the expressions that are its arguments.

A component called the common subexpression eliminator then looks for expressions that are always equal and merges them into a class. A new expression is first looked up among known ones; if it is new, it is simplified by rules such as `constant + constant = constant` or `X * 1 = X`. Because this recurses, the `X * 1` rule also applies when the "1" is a complicated expression the optimizer has proved equals one.

Some steps symbolically track what is at memory and storage locations. That is how a hash of data that was just written can be computed at compile time. The tracking has to be conservative: a write to location `l` erases the knowledge about any location that *might* equal `l`. For storage that means everything not provably different; for memory, everything that might lie within 32 bytes of `l`. Unrelated writes do not wipe the slate if the offsets are provably far apart.

When all jump targets are known, a control-flow graph can be built, and a `JUMPI` whose condition turns out constant becomes an unconditional jump (or vanishes). Take this kind of code:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Quota {
    uint256[10] private used;

    function check() external returns (uint256) {
        uint256 cap = 40;
        used[2] = 25;
        if (used[2] + 15 != cap) return 2;   // can never be true
        return 1;
    }
}
```

After the analysis the optimizer knows `used[2]` is 25, so the condition is false and the branch can be dropped, leaving little more than the storage write and a return of 1.

Finally each block is regenerated from its dependency graph: operations that are not part of what ends up on the stack or in memory or storage are dropped, side effects keep their original order, and needed values are produced in the right place. The new block replaces the old only if it is smaller.

**Simple inlining** (since 0.8.2). Calls to small internal functions compile to a jump into a block that ends with a jump back out. When the body is one continuous basic block, the "inliner" replaces the jump-in with a copy of the block; later steps tidy up the return jump. A heuristic decides whether this pays off over the contract's life, looking at the size of the function, how many places reference it and the `runs` value.

## The Yul-based module

This module is more powerful because Yul has no arbitrary jumps, so the side effects of each function can be computed. If one call does not touch storage and the next does, and their values do not depend on each other, the calls can be reordered. If a side-effect-free call is multiplied by zero, it can be deleted. Its main components are SSA conversion, common subexpression elimination, expression simplification, unused-assignment elimination and the full inliner, and it works as a **greedy** pipeline with no backtracking. The docs warn that the information is subject to change as the optimizer is under heavy development.

Every step has a one-letter abbreviation, and a **step sequence** is a string of those letters. You can supply your own:

```
solc --optimize --ir-optimized --yul-optimizations 'dhfoD[xarrscLMcCTU]uljmul:fDnTOcmu'
```

(In Standard JSON the same string goes in `optimizer.details.yulDetails.optimizerSteps`.) Reading that string:

- Letters before the colon are the **main sequence**, after it the **cleanup sequence**. If the colon is missing, your string is the main sequence and the default cleanup is used. A colon at the start gives an empty main sequence; at the end, an empty cleanup.
- `d` (VarDeclInitializer), `h` (FunctionHoister), `f` (BlockFlattener), `o` (ForLoopInitRewriter) and `D` (DeadCodeEliminator) run once first.
- The part in `[...]` is a **loop**: it repeats until the code stops changing or the maximum number of rounds (currently 12) is reached. It holds `x` (ExpressionSplitter), `a` (SSATransform), `r` (UnusedAssignEliminator, twice), `s` (ExpressionSimplifier), `c` (CommonSubexpressionEliminator), `L` (LoadResolver), `M` (LoopInvariantCodeMotion), `c` (the eliminator a second time), `C` (ConditionalSimplifier), `T` (LiteralRematerialiser) and `U` (ConditionalUnsimplifier). Brackets may appear more than once but cannot be nested.
- `u` (UnusedPruner), `l` (CircularReferencesPruner), `j` (ExpressionJoiner), `m` (Rematerialiser), then `u` and `l` once more finish the main sequence.
- After the colon, cleanup: `f D n T O c m u`: flatten, remove dead code, simplify control flow, rematerialise literals, restructure loop conditions, remove common subexpressions, rematerialise and prune.

The order matters, and a step can create chances for ones that already ran, which is why repeating helps. A few steps are hardcoded and always run before and after your sequence: the disambiguator (it gives every identifier a unique name, which every later stage relies on), the function hoister and grouper (which put code in a normal form of one block of statements followed by the function definitions) and the for-loop init rewriter.

## The codegen-based module

Two optimizations happen at code generation. In the old pipeline, a literal in a commutative binary operation is moved to the right-hand side, which helps use associativity. In the IR pipeline, almost everything is left to the Yul optimizer, but one case is done upfront because the high-level shape is clearer then: the **unchecked loop increment** (since 0.8.22). It lets an idiomatic loop increment its counter without the overflow check, so you do not need the manual `unchecked { ++i; }` trick.

It applies only when all of this holds:

- The condition is `i < Y` using the built-in `<` (not `<=`, not a user-defined operator), where `i` is a local counter of a built-in integer type.
- The update is `i++` or `++i`.
- Neither the body nor the condition expression modifies `i`.
- The comparison happens in the counter's own type: the right-hand side must be implicitly convertible to the counter's type, so that the counter is not widened first.

Eligible and not eligible:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

contract Loops {
    function yes(uint256 n) external pure returns (uint256 s) {
        for (uint256 i = 0; i < n; ++i) s += i;           // eligible
    }

    function noLessEqual(uint256 n) external pure returns (uint256 s) {
        for (uint256 i = 0; i <= n; ++i) s += i;           // <= is excluded
    }

    function noBodyWrites(uint256 n) external pure returns (uint256 s) {
        for (uint256 i = 0; i < n; ++i) { s += i; i += 1; } // body modifies i
    }
}
```

The last condition is subtle. In `for (uint16 i = 0; i < uint32(70000); i++)`, the counter is widened to `uint32` for the comparison, and a `uint16` never reaches 70000, so the condition never becomes false. The increment can really overflow, so the check must stay.

Test with the exact settings you will deploy with (optimizer on, the same runs value, the same pipeline), not just the defaults of your test tool.</div>
