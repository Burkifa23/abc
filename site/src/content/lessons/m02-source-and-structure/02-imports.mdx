A campus election contract grows. First it needs a voter list, then a counting routine, then the test suite wants to share helpers with it. One file stops being practical, so you split the code up and join the pieces with `import`. The syntax is short, but one question deserves a careful answer: how does the compiler turn the text between the quotes into a file? The answer is a small system of names, folders and rewrite rules. You meet it every time a lab says `import "forge-std/Test.sol";`.

## The import statement

Solidity borrows its syntax from modern JavaScript, with one difference: there is no "default export". Everything at file level is a named symbol, and you decide what to take.

```solidity
import "Registry.sol";                                  // 1. everything
import * as Reg from "Registry.sol";                    // 2. everything, behind a prefix
import "Registry.sol" as Reg;                           // 2b. same meaning as 2
import {Voter, Roll as VoterRoll} from "Registry.sol";  // 3. only these, one renamed
```

The text in quotes is the *import path*. Form 1 pastes every top-level symbol of `Registry.sol` (and of whatever it imported) into your file's global scope. It works but is discouraged: when the other file adds a new top-level name next month, the name silently appears in every file that imported it this way, and may clash with your own. Form 2 keeps those names behind `Reg.`, so you write `Reg.Voter`. Form 3 is usually best, because a reader sees exactly what you use, and `as` settles a name collision on the spot.

## Names, not folders: the virtual filesystem

If import paths pointed at real folders, a project that builds on Kwesi's Windows laptop might fail on Efua's Linux server simply because the paths differ. For reproducible builds the compiler hides the real disk. It keeps an internal table called the *virtual filesystem* (VFS), where every piece of source code has a unique **source unit name**. That name is an opaque label; it merely often looks like a path.

An import path is *translated* into a source unit name, which is then looked up in the VFS.

### What fills the VFS

The VFS starts with whatever you hand to the compiler:

- **Command line.** `solc Ballot.sol` registers the file under its path, tidied into a canonical form (explained below).
- **Standard JSON.** This is the structured input format used by tools like Foundry and Hardhat. The keys of its `sources` object become the source unit names directly, and they can be anything.
- **Standard JSON with `urls`.** Instead of source text you give a list of places to try. The compiler offers them one by one to the import callback until one works. The key is still the name, whichever address succeeded.
- **Standard input.** Piping code into `solc -` stores it under the name `<stdin>`.

After that, new files can only arrive through the **import callback**. When an import resolves to a name the VFS does not have, the compiler calls the callback and asks it to supply the code. The command-line compiler ships a basic callback, the *host filesystem loader*, which treats the name as a path on disk (switch it off with `--no-import-callback`). The JavaScript build has no callback unless you write one, which is why the exercises on this site compile exactly one file. Other tools offer richer callbacks: Remix, for example, can fetch from HTTP, IPFS or npm. If nothing can supply the name, compilation fails.

For portability, use forward slashes in import paths (they work everywhere) and avoid anything that depends on one callback or one operating system. Backslash handling and letter case differ between machines.

## Direct and relative imports

Every import path falls into one of two groups. A **relative** import starts with `./` or `../` and is read against the *source unit name of the importing file*. A **direct** import is anything else, and the path simply is the name.

```solidity
// inside the unit named contracts/vote/Ballot.sol
import "./Voter.sol";             // relative -> contracts/vote/Voter.sol
import "../lib/Count.sol";        // relative -> contracts/lib/Count.sol
import "contracts/lib/Count.sol"; // direct   -> contracts/lib/Count.sol
import "Voter.sol";               // direct   -> Voter.sol  (NOT the neighbour!)
```

That last line is a classic trap. `"Voter.sol"` is not `"./Voter.sol"`; it names a top-level entry in the VFS.

To resolve a relative import, the compiler starts from the importer's name and removes its last segment (the file name). Then it walks the import path from the left: a `.` is skipped, a `..` removes one more segment, and any other segment is appended after a single slash. Because names are not shell paths, nothing else is normalised. A `/./` or a doubled slash inside a *direct* name stays exactly as typed, so `/lib/math.sol` and `/lib/../lib///math.sol` are two different units to the VFS, although a disk may treat them as one file. Even if the loader reads one disk file for both names, the compiler still sees two source units. The part contributed by the import path is tidied the Unix way, while the importer's own name is left untouched, which stops an `https://` prefix from collapsing into `https:/`.

Leading `..` segments get brittle fast. The docs advise using direct imports with a base path and include paths instead.

## Base path and include paths

When the host filesystem loader needs a name, it glues the **base path** in front and checks the disk. If nothing is there, it repeats with each **include path**, in order. A sensible set-up is the project root as base path and library folders as include paths.

```text
solc Ballot.sol --base-path . --include-path node_modules/ --include-path /usr/local/lib/node_modules/
```

Now `import "@openzeppelin/contracts/utils/Strings.sol";` works whether the library sits in the local folder, the global folder, or inside your tree, and the build produces identical metadata. The default base path is empty, which leaves names untouched (the only setting where absolute names mean real absolute paths). Include paths need a non-empty base path and cannot be empty strings. Paths may overlap, but if one name matches existing files under two of them, the compiler reports the ambiguity.

### How command-line files get their names

A file named on the command line must receive the same name wherever the compiler runs. So its path is made absolute, `.` and `..` are collapsed, separators become `/`, a drive letter that matches the working drive becomes `/`, and symbolic links are left alone. Then the compiler tries the base path and, failing that, each include path, and strips the one that is an exact prefix. What remains is the name. If that result would not be unique, you get an error. Before version 0.8.8 this stripping did not exist, so old compilers want you to run them from the base path.

## Allowed paths

Reading arbitrary files is risky, so the loader only reads from a short list of safe directories. Outside Standard JSON mode, those are the folders of files named on the command line, the folders of remapping targets, and the base and include paths. In Standard JSON mode the list shrinks to the base path and include paths. Extra folders are whitelisted with `--allow-paths`, a comma-separated list. The compiler does not verify that they exist, and the comparison is case-sensitive. Links do not extend the list: a file reachable only through a symlink that leads outside the allowed set is refused.

That explains two lines in the labs' `foundry.toml` that look redundant:

```toml
remappings = ["forge-std/=/opt/forge-std/src/"]
allow_paths = ["/opt/forge-std"]
```

The first rewrites names. The second tells the loader that `/opt/forge-std` is a place it may read, because the remapping target alone does not grant access when Foundry drives the compiler through Standard JSON.

## Import remapping

A *remapping* edits the translation from import path to source unit name. It has the shape `context:prefix=target`.

- `prefix` must match the *start* of the name produced by the import. It cannot be empty.
- `target` replaces that prefix. It may be empty, which deletes the prefix.
- `context` (optional) must match the start of the name of the file that holds the import, so you can limit a rewrite to one library. An empty context means every file.

In a lab, `forge-std/=/opt/forge-std/src/` turns `forge-std/Test.sol` into `/opt/forge-std/src/Test.sol`, and the loader reads that file. With contexts you can give two libraries two versions of the same dependency: `lib1:oz/=oz-v4/` and `lib2:oz/=oz-v5/`.

The rules, in short:

1. Remappings change only the step from import path to name. Names added another way (command-line files, `urls` in Standard JSON) are never remapped.
2. Context and prefix are compared with *names*, so you cannot remap `./`, but you can remap the folder name that `./` expands to. A base path added internally cannot be remapped at all.
3. The target is pasted in as is, with no normalisation and no automatic trailing slash. `/p/=/q` turns `/p/x.sol` into `/qx.sol`. A target starting with `./` is relative to the base path, not to the importing file.
4. Matching is plain text and partial names count: `/newProject/con:/new=old` matches `/newProject/contract.sol` and yields `oldProject/contract.sol`. `a//b` does not match `a/b`.
5. At most one remapping applies per import. The longest matching context wins, then the longest prefix, then the one written last. Remappings never chain, so `a=b b=c` leaves `a` as `b`.

Remappings are stored in the contract metadata, and a hash of the metadata is embedded in the bytecode. Any change to a remapping therefore changes the bytecode. Keep personal paths such as `/home/ama/...` out of targets; an include path is the safer way to point at a library folder.

## URLs in imports

Prefixes like `https://` or `data://` mean nothing special in an import path. They are just characters in a name. The one exception is `file://`, which the host filesystem loader strips. To build locally from code that imports a web address, remap the protocol and domain onto a local clone:

```text
solc :https://github.com/ethereum/dapp-bin=/usr/local/dapp-bin contract.sol
```

The leading colon is needed because the context is empty. Without it the compiler would read `https` as the context.

<div class="callout"><strong>Watch out.</strong> An import without <code>./</code> is never "next to this file". <code>import "Voter.sol";</code> looks for a unit literally named <code>Voter.sol</code> at the top of the VFS. If you meant the neighbour, write <code>./Voter.sol</code>.</div>
